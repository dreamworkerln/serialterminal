## 1. Вердикт

**Существующую систему стоит исправлять по границам ответственности, без полной переписки и без внедрения FLOW/CAPS/QUERY сейчас.** Сначала исправить потерю состояния и ошибочные переходы в SerialTerminal, затем укрепить локальный машинный интерфейс ST ↔ Chatter. Текущий LoRa USER/ACK и FT1 v1 сохранить.

Нынешняя проблема не сводится к недостаточному количеству подтверждений. Есть конкретные дефекты: исключения оставляют фоновые обработчики без рабочего продолжения, отдельная ошибка удаляет накопленный файл, уже полученный отказ не останавливает передачу, судьба принятого сообщения теряется между очередями. Новый радиопротокол этих ошибок не исправит.

Ограничения этой рекомендации:

- прошивка остаётся прототипом текущего stop-and-wait USER/ACK;
- будущие пакетные передачи LoRa SACK и ACK с битовой маской не реализуются;
- нормальная передача не получает дополнительных служебных радиопакетов;
- размер текущего BINARY USER и полезного FT1 DATA сохраняется: 243 и до 227 байт соответственно;
- firmware не узнаёт имена файлов, FT1 transfer_id, chunk_index, файловый bitmap или durable progress;
- восстановление конечно; ошибки видны; пригодное состояние сохраняется;
- новый общий документ выбран вместо двух новых TODO, чтобы не дублировать уже существующие задачи и не менять их authoritative inventory без реализации.

## 3. Какие подтверждения уже существуют

```text
ST A → USB/BLE → node A → LoRa → node B → USB/BLE → ST B → файл
```

| Событие | Что можно из него заключить |
|---|---|
| Session `written` | Локальный transport сообщил завершение записи; это ещё не приём команды firmware |
| Локальный `> [BINARY]` | Сигнал текущего firmware submission path; не подтверждение удалённого ST |
| Firmware USER ACK | Peer node приняла радиотранзакцию; не подтверждение локального USB/BLE вывода peer |
| FT1 RESUME | Точка продолжения, которую сообщил receiver; текущий active-META путь ещё требует исправления durable semantics |
| FT1 MISSING | Запрос отсутствующих частей файла |
| FT1 RESULT OK | Должен означать успешную проверку и надёжную публикацию файла; порядок публикации нужно укрепить |

В `Scheduler::handleUserFrame()` USER уже попадает в dedup history и создаётся ACK obligation перед выводом BINARY в терминал. Дубликат радио-USER подтверждается повторно, но повторно в host не выводится. `TerminalIo::output()` игнорирует результат помещения фрагмента в USB/BLE очередь.

Поэтому **RF ACK возможен при потере DATA между node B и ST B**. Повтор того же радио-USER не обязан восстановить такой DATA. FT1 repair отправляет ту же файловую identity новой host submission, и это правильно.

Менять смысл RF ACK на «файл записан на компьютере» нельзя: это привяжет радиопротокол к подключённому host и файловой системе и сильно осложнит будущий SACK.

## 4. Приоритетные исправления SerialTerminal

### ST-1. Жизненный цикл transport и каждой принятой отправки

Исходники: `transports/serial.py:456`, `session.py:624`, `profiles/chatter/binary_user.py:356`, `profiles/chatter/binary_pipeline.py:281`.

`SerialTransport.write()` не проверяет возвращённую длину записи, ловит ограниченный набор исключений и превращает пойманные write/flush ошибки в обычный `TransportError`. Generic session повторяет такие сообщения. Исключение вне этого набора может закончить TX worker, оставив принятый tx_id без результата.

Нужно:

- нормализовать ошибки backend на его границе, включая Linux `termios.error`;
- различать доказанное отсутствие записи и возможную частичную/полную запись;
- после возможной записи возвращать `unknown`, не разрешать слепой generic replay;
- контролировать short write;
- гарантировать каждому принятому tx_id наблюдаемый исход либо явно ограниченное ожидание;
- добавить адресное снятие ещё не начатой отправки и механический drain/fence для своих отправок;
- не считать очистку correlation deque отменой transport queue или firmware queue;
- освободить lease только после учёта собственных outstanding операций; чужие операции не отменять;
- сделать неожиданный выход worker видимым, завершать/приостанавливать зависимые операции.

Состояния вроде queued/writing/written/unknown относятся к generic session. Команды Chatter и правила FT1 replay туда не попадают.

### ST-2. Ошибка попытки не должна автоматически удалять файл

Исходники: `file_transfer/core.py:1253`, `:1269`, `:1328`, `:1577`; `resumable.py:384`, `:464`.

В текущем коде неверный index, конфликтующий duplicate, неправильный END, переполнение MISSING и ошибка отправки MISSING могут приводить к удалению `.part` и manifest. Существующий wrong-length fix закрывает только один из этих случаев.

Выбрать следующую таблицу поведения:

| Причина | Действие | Сохранённое состояние |
|---|---|---|
| Неверная длина/index DATA, некорректный END | Reject отдельного сообщения; событие ошибки; конечное ожидание корректного control | Хорошие chunks сохранить |
| Идентичный DATA duplicate | Идемпотентный no-op | Сохранить |
| Один index, разные правдоподобные bytes | Приостановить как identity/integrity conflict | Сохранить для разбора; не считать сомнительный bitmap доказательством |
| Потеря MISSING/RESULT/local echo | Ограниченное восстановление соответствующего сообщения | Identity и пригодный partial сохранить |
| Recovery/idle timeout | Завершить текущую попытку или suspend с причиной | Разрешить явно определённый resume |
| Ошибка диска/checkpoint | Остановить продвижение durable state, показать отказ | Сохранить последний подтверждённый checkpoint насколько позволяет storage |
| Итоговый hash/decompression conflict | Не публиковать файл, quarantine | Не использовать сомнительные данные для автоматического skip |
| Явный cancel | Отдельная намеренная операция | Cleanup согласно документированному контракту |

По конфликтующим копиям я согласен с более осторожным GPT-review: **не выбирать автоматически последнюю копию и не обещать точечное восстановление без независимого доказательства правильных bytes**. Итоговый SHA-256 не показывает, какой чанк повреждён.

В `_start_new_incoming()` отдельно исправить удаление чужого retained `.part` при неудачной попытке создания: удалять можно только временные файлы, действительно созданные этой операцией.

### ST-3. Remote failure должен останавливать новые DATA

Исходники: `core.py:1034`, `:887`; `resumable.py:652`; `pipeline_manager.py:80`.

RESULT сохраняется, но обычная, pipelined и repair отправка преимущественно проверяет cancel. В итоге передатчик продолжает занимать эфир после отказа принимающего ST.

Проверять remote terminal outcome перед каждой новой submission и после любого wait/recovery. Будить coordinator отдельным событием. Не подменять это `cancel_event`: Chatter adapter использует его для `/cancel all`.

Уже выданные tickets учесть и завершить bounded способом. Число tickets ≤2 не означает, что в firmware всегда осталось не более двух RF операций: local echo приходит до завершения ACK, а старые операции могут жить ниже adapter. Обязателен учёт очередей по ST-1.

### ST-4. Восстановление и durable state должны сохранять identity

Исходники: `resumable.py:70`, `:317`, `:552`; `manager.py:211`, `:314`; `resume_source.py:55`.

- Lost local echo не доказывает потерю DATA. После разрешения судьбы старого ticket допустим bounded replay только идемпотентного FT1 сообщения с теми же bytes/id/index.
- Не добавлять все timeout/rejection в recoverable set одной строкой: это оставит старые записи в очередях и создаст новые копии.
- Повторный start того же failed transfer в том же процессе должен иметь явный same-ID resume. Сейчас наличие ID в `_records` заставляет выбрать новый ID, хотя journal сохранён.
- Ответ RESUME active receiver должен вычисляться по durable map либо после успешного checkpoint. Сейчас `_send_resume()` использует memory map, которая может опережать manifest.
- Restore/revive, claim lease и смена `_active_id` должны быть атомарны с rollback при неуспехе.
- Prepared wire representation должна оставаться неизменной. Для `Compression.NONE` текущий путь снова читает исходный пользовательский файл; нужен snapshot/spool, проверяемый также при resume.
- Вложенные ожидания должны получать остаток общего monotonic deadline. Текущие 60 секунд local recovery не являются строгим общим пределом всех вложенных ожиданий.

### ST-5. Явно довести durable publication до RESULT OK

Исходники: `core.py:1450–1520`, `:1521`; `resumable.py:472`; `resume_store.py:236`.

Дополнительный вывод по коду: core публикует destination и отправляет RESULT OK, а resumable-обёртка сохраняет completed tombstone уже после возврата из core. У распакованного `.verified` файла нет явного fsync перед публикацией; перед RESULT не виден fsync каталога destination.

Рекомендуемый порядок:

```text
проверить wire hash / original hash / размеры
→ подготовить и fsync окончательные bytes
→ durable publishing intent с тем же выбранным destination
→ атомарно опубликовать destination
→ fsync каталога destination
→ durable completed tombstone
→ RESULT OK
→ cleanup больше не нужного partial/manifest
```

Destination нельзя независимо выбирать до и после publishing intent: одна операция должна владеть одним местом публикации. После crash каждый промежуточный этап должен однозначно восстанавливаться, без второй публикации.

Это вывод о порядке операций, **не результат воспроизведённого отключения питания**. Atomic rename сам по себе не доказывает сохранность файла после потери питания.

Также decoder RESULT должен отвергать противоречие `ok=True` и failure code. Это исправляется без новых bytes в радио. Оно не превращает legacy RESULT в криптографически защищённое сообщение и не устраняет любой вариант порчи.

### ST-6. Один владелец FT1 scheduling вместо наращивания наследования

Сохранить общий transport/session и profile segregation. Постепенно заменить цепочку из четырёх manager-классов композицией:

```text
FT1 coordinator
  ├─ sender / receiver state
  ├─ immutable source + durable store
  ├─ codec
  └─ один bounded outbound lane через BinaryUserTransport
```

RX worker принимает и проверяет сообщения, обновляет состояние/передаёт работу storage и ставит ответы в bounded outbox. Он не ждёт завершения USB/BLE/RF отправки ответа. Не создавать thread на каждый RESULT. Ограничить RX/control queues; overflow должен иметь видимый исход, а не молчаливую потерю.

Отдельно защитить idle sweep: сейчас исключение оттуда может закончить RX worker. Исключения callback/storage не должны исчезать в `except Exception: continue` без события и решения о состоянии transfer.

На первом этапе достаточно убрать O(n) пересчёт `sum(received.values())` на каждый DATA и вести счётчик инкрементально. Полная замена dict на сложное дерево интервалов для прототипа не является блокером. Выбрать bitmap/ranges и ограничения размера по реальным требованиям позже.

### FW-2. Отделить машинные BINARY события от человеческой печати

Исходники: `Scheduler.cpp:724`, `:1560`; `TerminalIo.cpp:1065`, `:1099`, `:1164`, `:1241`, `:1371`.

Сейчас пользовательское форматирование, output mode и общие очереди являются частью машинного пути доставки. В TELEMETRY-only режиме Chatter adapter вообще не может использовать BINARY presentation. Отказ USB/BLE queue не возвращается вызывающему коду как результат доставки.

Минимальное направление:

1. Внутри firmware выделить typed BINARY RX/TX/status события и bounded очередь полных сообщений.
2. Вывод в человеческую консоль сделать отдельным потребителем этих событий.
3. Для машинного потребителя ввести локальный идентификатор submission и адресный result/rejection; он не передаётся по LoRa.
4. Различать queue accepted, physical TX outcome, link outcome и unavailable. Принятие в очередь не выдавать за доставку.
5. Явно учитывать drops, high-water mark, short USB writes и BLE timeout/stale drops. Не печатать диагностику только через ту же переполненную очередь: счётчики должны сохраняться в RAM и читаться позднее.
6. Задать ownership для USB/BLE machine session, её epoch и outstanding submissions. Две активные host-сессии не должны конкурировать за неадресованные echo/errors.
7. Сохранить RF RX/ACK приоритет; не блокировать Scheduler на USB/BLE или fsync.

Локальный credit должен отражать зарезервированную реальную ёмкость admission/queue. Его нельзя выдавать повторно только потому, что transport завершил запись. Сначала оставить окно 2; расширение — отдельная задача производительности.

### FW-3/ST-7. Защитить USB/BLE кадрирование без радио-overhead

**CRC и служебную корреляцию сначала добавить на локальную границу host ↔ node, а не внутрь каждого LoRa DATA.**

Предлагаемый контракт машинного режима: version, epoch/request identity, type, length, payload, checksum для всей значимой локальной записи. Одинаково защищать входящие команды и исходящие BINARY/status записи. Можно сохранить текст/base64 encoding на первом этапе; важен проверяемый frame и однозначная синхронизация.

На sender node оболочка проверяется и снимается до построения радио-USER; receiver node создаёт новую локальную оболочку из уже принятого radio payload. FT1 bytes и radio frame остаются прежними. Это защищает локальные участки, в том числе доставку legacy RESULT, без уменьшения 227-byte DATA.

Обязательные свойства:

- повреждённый машинный frame целиком отвергается; его остаток не становится обычным USER текстом;
- обрыв/склейка/потеря delimiter имеют bounded resynchronization;
- USB restart/reconnect не склеивает хвост прежней команды с новой;
- epoch проверяется до применения outcome; старый ответ не закрывает новую submission;
- machine channel не зависит от `/chat` / `/tele` / `/both`;
- локальное согласование версии происходит с нодой, не требует новых FT1 CAPS в эфире;
- старый human terminal остаётся доступен; legacy machine mode имеет явные ограничения;
- нет обязательного отдельного round trip на каждый DATA только ради локального credit;
- формат и числа новых полей закрепляются отдельным небольшим контрактом до реализации, а не объявляются уже существующим API.

Такой CRC не доказывает durable приём удалённым ST, не спасает от потери целой записи, не защищает от повреждения до его вычисления и не заменяет final SHA. В прототипе оставшиеся потери чинит существующий FT1 END/MISSING. Не обещать неограниченное хранение RX в RAM ноды при отключённом компьютере.

### FW-4. Silent-deaf RX расследовать отдельно от FT1

Исходники: `RadioService.cpp:272`, `RadioHealthMonitor.cpp:27`; pinned RadioLib `SX1278.cpp:654`.

RegVersion подтверждает SPI/digital liveness. OpMode + DIO mapping подтверждают проверенные регистры RX entry. Ни то ни другое само по себе не доказывает успешный приём peer.

В локальной RadioLib 7.7.1 действительно есть RX errata операции с непередаваемыми наверх ошибками и прямые записи 0x36/0x3A. При 470 MHz/BW500 это обоснованный кандидат для диагностики, но не установленная причина deaf state.

План: расширенные локальные before/after snapshots на переходах/ошибках; RX-only restart до собственного TX; известный peer frame; сравнение BW500 с BW250/125. Усиливать readback по ожидаемым конфигурационным значениям, не сравнивать динамические IRQ/FIFO регистры с вечными константами. Не делать reset по одному отсутствию трафика и не вводить новые регулярные RF probes.

`RADIO_UNAVAILABLE` оставить терминальным до явного восстановления оператором. ST показывает причину и сохраняет transfer. Автоматический `/reboot` по отсутствию remote progress в этот план не входит.

## 6. Что делать с большим FLOW-дизайном TODO_041

Оба review полезны в анализе отказов. Их рекомендацию сразу строить новый end-to-end FLOW слой я **не принимаю как следующий этап для текущих ограничений**.

Отложить runtime implementation:

- FLOW/QUERY/CAPS handshake и runtime tokens;
- periodic durable credit и midstream repair;
- DATA_CHECKED со снижением полезной нагрузки 227 → 223;
- новые control types и protected envelopes на радиоуровне;
- дополнительные watchdog loops из TODO_038.

Сохранить дизайн как DEFERRED-направление, а TODO_041 разделить содержательно на «исправления FT1 v1» и «будущее расширение». Старые тексты не удалять и completed статус не ставить.

### Цена ограничения по эфиру

Нельзя одновременно гарантировать:

1. отсутствие дополнительной информации от remote ST до END;
2. немедленное обнаружение его смерти/отключения, пока peer node продолжает ACK;
3. непрерывную передачу без ожиданий.

Локальный host этого не знает. **Для текущего прототипа выбираем нулевой дополнительный служебный эфир на нормальном DATA-пути и честно оставляем обнаружение remote-host silence до существующего handshake/finalization.** Риск: часть или весь остаток файла может уйти без получателя. Не показывать sender progress как durable remote progress.

Если ранняя остановка по исчезновению принимающего ST станет обязательной, потребуется отдельное решение с измеренным бюджетом редких end-to-end сообщений. Не обещать решить это только местными таймерами или RF ACK.

### Legacy limits не прятать

При capacity 243 legacy MISSING содержит максимум `(243 − 13) // 8 = 28` ranges. Большой непрерывный пропуск — один range; множество одиночных пропусков исчерпывает лимит.

Сейчас исправить разрушительное поведение: сохранить partial и показать `repair_limit`/explicit resume. Matching META/RESUME может продолжить с earliest missing, но повторит suffix и поэтому не является бесплатной selective repair. Не дробить legacy full-set MISSING молча на несколько пакетов. Отказ от нового протокола означает сохранение этого ограничения на текущем этапе.

### Как считать overhead позднее

Любой новый FT1 QUERY или FLOW — обычный reliable USER и расходует также RF ACK, half-duplex turnaround, возможные retries и время ожидания. Query+reply — минимум две USER передачи и их ACK, а не только несколько metadata bytes.

Сравнивать:

`additional airtime = control USER + their ACK + retries`

плюс отдельно wall-clock простои. Считать полезные original bytes / полное время; baseline сохранять при одинаковых файле, PHY, topology и compression. Значения 10 секунд/256 chunks из TODO — гипотезы, не принятие по умолчанию.

## 7. Граница для будущего LoRa SACK

Сегодня нужно сохранить возможность заменить механизм доставки радио-USER, не протаскивая его детали в FT1.

```text
FT1: file identity, storage, END/MISSING/RESULT
  ↓ opaque BinaryUserTransport
Chatter host profile: local machine protocol, tickets, lifecycle
  ↓ USB/BLE
Firmware local adapter: bounded byte-message admission/events
  ↓ opaque USER service
Link reliability: нынешний USER/ACK; будущий batch/SACK здесь
  ↓
RadioService: SX1278 mechanics
```

FT1 не должен знать RF sequence, размер будущего batch или формат ACK bitmap. Firmware не должен знать файловые offsets.

Текущий `RadioOperationOwners` содержит один owner на класс операции. Это нормально для нынешнего stop-and-wait. Нельзя объявлять его уже готовым для нескольких одновременно outstanding USER в будущем SACK. Расширение owner/window model выполняется вместе с отдельным SACK этапом, с сохранением нынешних behavioral tests.

Не требуется сейчас универсальная HAL или система плагинов для нескольких гипотетических ARQ. Достаточно узкой границы и честно сформулированных invariant.

## 9. Критерии приёмки будущих исправлений

Это план проверок; по просьбе пользователя сейчас они не запускаются.

- Short/partial write, flush error, worker exception: ни accepted tx без исхода, ни слепого generic replay.
- Bad DATA/index/END, MISSING failure: остальные корректные chunks не удаляются.
- Negative RESULT останавливает новые DATA в original/pipeline/repair и не отправляет `/cancel all`.
- Lost echo после реальной доставки: finite same-message recovery, без бесконтрольного накопления старых tickets.
- Same-process/process-restart resume сохраняет transfer identity и неизменные bytes.
- RESUME не опережает durable map; fault во время fsync/manifest не создаёт ложного durable evidence.
- Crash на каждом этапе публикации: RESULT OK не предшествует принятому durable commit, нет двойной публикации.
- Corrupt local frame, потеря части base64, reconnect: reject целой записи, без превращения хвоста в RF USER.
- Queue overflow/drop: наблюдаемый счётчик/событие, bounded память; RF RX/ACK остаются приоритетными.
- Existing USER/ACK bytes, лимиты попыток, dedup и recovery correlation сохраняются.
- Физические USB/BLE, reset и deaf-RX сценарии имеют отдельные evidence; native тест не считается доказательством исправности железа.
- Нормальный DATA-путь не получил новых FT1 control сообщений по LoRa; скорость сравнивается с исходным baseline.

Итоговое решение: укрепить существующий транспорт и восстановление, а дополнительный радиопротокол вводить только когда его необходимость и цена подтверждены. Самые срочные проблемы находятся в текущей реализации, и для их устранения новый SACK/FLOW не требуется.
